Overview

A high-level summary of the topic

Py

Query optimization is the practice of writing SQL so the database does less work to give you the same answer.

Think of a large library where the stacks hold millions of books — a database is that library, and every query you run is a request to find specific information inside it. A well-optimized query uses the library's catalog to jump straight to the right shelf. A poorly written query makes the librarian walk every aisle and read every title.

Indexes

The catalog — points you to the right shelf

The fast path to specific rows, skipping the rest of the table.

Execution Plans

The route map — shows exactly where to look

The database's step-by-step route, visible before it reads any data.

Column Selection

The chapter — only what you came to read

Fetching only the columns you need reduces what gets carried back.

Slow-Query Patterns

The full-shelf sweep — every book, every time

If you already use VLOOKUP in Excel, you understand the core idea: looking up a value by its key is always faster than scanning every row from top to bottom — and indexes work exactly the same way in SQL.

Key Takeaways

The most important ideas to remember

SELECT * Costs More Than You Think

When you write SELECT * in a report query, the database retrieves every column in the table and sends it across the network — even columns your dashboard never displays — which means every extra column increases memory use, transfer time, and the chance of hitting a row-size limit on wide tables.

SELECT * Column Pruning Network Cost

Indexes Only Help Filtered Columns

An index on a column pays off when you filter or join on that column in a WHERE or ON clause; if you filter on an unindexed column instead, the database still scans every row, so the index you added offers no benefit at all — you have to add the index on the column you actually search by.

WHERE Clause Index Match Full Table Scan

EXPLAIN Shows the Actual Plan

Running EXPLAIN before your SELECT is the SQL equivalent of checking Google Maps before a trip — it shows you the route the database will take, lets you spot a full-table scan before it slows down your dashboard, and confirms whether your index is actually being used.

EXPLAIN Seq Scan Index Scan

Key Concepts

Column selection, WHERE filtering, indexes, JOIN efficiency, and EXPLAIN.

SELECT * vs Named Columns

Ask only for the columns you need.

Column Pruning

Column pruning means listing the column names you actually need instead of SELECT *. Fewer columns means less data over the wire and less memory used.

Column Selection Rules

Use SELECT * only when exploring prod ✗
List the columns you need good ✓
Skip wide text or BLOB columns faster ✓
SQL 
-- Reads every column, even ones you do not need
SELECT * FROM customers;

-- Reads only the two columns the report uses
SELECT customer_id, email FROM customers;

Listing columns also keeps your query stable when someone adds a new column to the table later.

WHERE Filtering

Operators that keep filters index-friendly.

Operators

WHERE filtering tells the database which rows to keep. The operator you choose decides whether the database can use an index or has to scan every row.

WHERE Operators

Op Meaning Example
= Exact match status = 'paid'
>= Range start order_date >= '2024-01-01'
IN Match a list region IN ('EU', 'US')
LIKE Pattern match email LIKE '%@acme.com'
SQL 
-- Index-friendly: compares the raw column to a value
SELECT order_id FROM orders
WHERE order_date >= '2024-01-01';

-- Index-unfriendly: wraps the column in a function
SELECT order_id FROM orders
WHERE YEAR(order_date) = 2024;

Keep functions off the column. Compare the raw column to a literal value so the index can still be used.

Indexes

Indexed vs unindexed lookup behavior.

Index Lookup

An index is a sorted lookup structure on a column. It lets the database jump straight to matching rows instead of reading every row in the table.

Indexed vs Unindexed Column

Indexed Unindexed
Plan node Index Scan Seq Scan
Rows read Only matching rows Every row in the table
Speed at scale ✓ Fast ✗ Slow
SQL 
-- Create an index on the column you filter on most
CREATE INDEX idx_orders_customer ON orders (customer_id);

-- This filter can now use the index for fast lookup
SELECT order_id, total
FROM orders
WHERE customer_id = 482;

Indexes cost write speed. Each INSERT or UPDATE has to update the index too — only index columns you filter on often.

JOIN Efficiency

Filter early, join on indexed keys.

JOIN Rules

A JOIN combines rows from two tables on a matching key. Each extra join multiplies the work, so cut the row count and use indexed keys.

JOIN Rules

Join on indexed id columns fast ✓
Filter rows before joining good ✓
Avoid joining on unindexed text slow ✗
SQL 
-- Join on indexed keys, filter before joining
SELECT o.order_id, c.email
FROM orders AS o
JOIN customers AS c ON c.customer_id = o.customer_id
WHERE o.order_date >= '2024-01-01';

Filter first, join second. Push WHERE clauses as early as possible so the join works on a smaller row set.

EXPLAIN

Read the query plan before you tune.

Query Plan

EXPLAIN shows the plan the database will use to run a query. It tells you whether each step is an index scan or a full table scan, without running the query.

Plan Nodes To Watch

Index Scan on filter column good ✓
Seq Scan on a large table slow ✗
High rows estimate check ⚠
SQL 
-- Show the query plan without running the query
EXPLAIN
SELECT order_id, total
FROM orders
WHERE customer_id = 482;

Run EXPLAIN before tuning. Confirm the plan changes from Seq Scan to Index Scan after adding an index.

Code Examples

Hands-on code snippets to explore the concepts

01

Select Named Columns

Beginner Orders Column Pruning

What This Does

This query asks the orders table for only the two columns the report needs. Naming columns instead of using SELECT * sends less data over the network.

select_named_columns.sql 
-- Ask the orders table for two columns only
SELECT order_id, total_amount
FROM orders;
Terminal $ psql -f select_named_columns.sql
order_id | total_amount
10231 | 84.50

If your table has 30 columns and your report uses 2, you are pulling 15× more data than you need.

02

Filter With WHERE

Beginner Transactions Index-Friendly

What This Does

This query filters transactions to a single month using a raw date range. Comparing the column directly to a literal date lets the database use its index on txn_date.

filter_with_where.sql 
-- Keep only transactions made in April 2026
SELECT txn_id, amount
FROM transactions
WHERE txn_date >= '2026-04-01'
  AND txn_date <  '2026-05-01';
Terminal $ psql -f filter_with_where.sql
txn_id | amount
4821 | 129.00

Compare the raw column to a date — never wrap it in a function like YEAR(txn_date), or the index is skipped.

03

Read EXPLAIN Output

Beginner Customers Query Plan

What This Does

Putting EXPLAIN in front of a query asks the database to show the plan it would use, without running it. The output tells you whether the filter uses an index scan or a slow full-table scan.

read_explain_output.sql 
-- Show the query plan instead of running the query
EXPLAIN
SELECT customer_id, email
FROM customers
WHERE customer_id = 482;
Terminal $ psql -f read_explain_output.sql
Index Scan using customers_pkey on customers
Index Cond: (customer_id = 482)

If you see Seq Scan on a large table, add an index on the column you filter on most.

Common Mistakes

Frequent errors and how to avoid them

Using SELECT * Instead of Named Columns

SELECT * fetches every column in the table, including ones you never use, slowing the query down.

Pitfall

SELECT * tells the database to read and send every column across the network. Name only the columns your report needs — every extra column adds transfer time and memory use.

Wrong — fetches all columns 

SELECT *
FROM orders
WHERE order_date >= '2024-01-01';

Correct — named columns only 

SELECT order_id, order_date, revenue  -- only what you need
FROM orders
WHERE order_date >= '2024-01-01';  -- filter early

Think of it like ordering a meal — you wouldn't ask for the entire menu just to eat one dish. Name the columns you actually need, and the database does far less work.

Wrapping an Indexed Column in a Function

Applying a function to an indexed column in WHERE forces a full table scan, ignoring the index entirely.

Pitfall

When you write WHERE YEAR(order_date) = 2024, the database must call that function on every single row before it can filter — the index on order_date is never used. Filter on the raw column value instead so the index can kick in.

Wrong — function hides the index 

SELECT order_id, revenue
FROM orders
WHERE YEAR(order_date) = 2024;

Correct — raw column, index used 

SELECT order_id, revenue
FROM orders
WHERE order_date >= '2024-01-01'  -- index can scan this
  AND order_date < '2025-01-01';   -- upper bound keeps it tight

An index is like a sorted bookmark — it only works when the value you're searching for matches a bookmark exactly. Wrapping the column in YEAR() scrambles the value so the bookmark is useless.

Running a Slow Query Without Checking EXPLAIN First

Executing a query directly on a large table without reading the execution plan wastes time you could avoid.

Pitfall

Running a query cold on a large table means you only find out it's slow after waiting. Prefix it with EXPLAIN first — you'll see whether the database chose a sequential scan (slow) or an index scan (fast) in under a second, with no data read.

Wrong — run blind, find out late 

SELECT customer_id, SUM(revenue)
FROM transactions
GROUP BY customer_id;

Correct — check the plan first 

EXPLAIN                          -- shows the plan, reads no data
SELECT customer_id, SUM(revenue)
FROM transactions
GROUP BY customer_id;

EXPLAIN is free — it costs nothing to run and shows you the route before you drive it. Make it a habit for any query touching a table you haven't profiled before.
