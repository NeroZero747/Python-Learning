Overview

A high-level summary of the topic

Py

A SQL join combines rows from two tables by matching a shared column — and the join type controls what happens to rows that have no match.

Think of joins like matching two spreadsheets side by side: an invited-guests list and a check-in log. An INNER JOIN only keeps guests who appear on both lists. But what about the guest who was invited but didn't show up, or the walk-in who never made the list? Each advanced join type decides what to do with those unmatched rows.

LEFT JOIN

All invited — whether checked in or not

Keeps every row from the left list, filling blanks where no match exists.

RIGHT JOIN

All check-ins — invited or walk-in

Keeps every row from the right list, even when the left has no match.

FULL OUTER JOIN

Every name from both lists, no one left out

Keeps all rows from both lists, placing nulls wherever a side has no match.

Self Join

One list compared against itself

Matches rows within the same table to uncover hierarchies and related pairs.

If you already use VLOOKUP in Excel to combine two sheets, SQL joins are the same idea — just more powerful and able to handle mismatched rows that VLOOKUP simply drops.

The most important ideas to remember

NULL Means No Match Found

When an outer join keeps an unmatched row, every column from the other table is filled with NULL — the same NULL you saw in the NULL Handling lesson, so you can test for it with IS NULL or COALESCE.

Any table that stores a reference to another row in the same table — such as an employee's manager ID — can be queried with a self join to produce readable parent–child pairs like "Alice reports to Maria".

Key Concepts

LEFT/RIGHT/FULL OUTER joins, self joins, cross joins, and how to choose.

OUTER JOINs

What each outer join type keeps in the result

SQL Clause

An outer join keeps rows from one or both tables even when no matching row exists on the other side. The columns from the non-matching side are filled with NULL. Use it whenever you cannot afford to silently lose rows.

LEFT JOIN vs FULL OUTER JOIN

LEFT JOIN FULL OUTER
All left rows ✓ Yes ✓ Yes
All right rows ✗ Matched only ✓ Yes
Use for Rows missing from right All unmatched rows
SQL 
SELECT
    c.name,         -- always shown (left table)
    o.order_id      -- NULL when no orders exist
FROM customers c
LEFT JOIN orders o  -- keep every customer row
ON c.id = o.customer_id;

Add WHERE o.order_id IS NULL after a LEFT JOIN to find customers who have never placed an order — a very common reporting pattern.

Self Join

Querying a table against itself using aliases

SQL Technique

A self join connects a table to a copy of itself. You give each copy a different alias so SQL can tell them apart. It is useful whenever one column in a table points back to another row in the same table — for example, a manager_id that references employee_id.

SAME TABLE — TWO ALIASES

employees AS e Staff side
=
employees AS m Manager side
→
One table
SQL 
SELECT
    e.name AS employee,    -- row from the staff alias
    m.name AS manager      -- row from the manager alias
FROM employees e           -- first copy: staff
JOIN employees m           -- second copy: managers
ON e.manager_id = m.employee_id;

Use a LEFT JOIN instead of JOIN when the top of your hierarchy (e.g. the CEO) has no manager — a regular JOIN silently drops that row from the result.

CROSS JOIN

Every row paired with every other row

SQL Clause

A CROSS JOIN pairs every row in the first table with every row in the second table. If table A has 5 rows and table B has 4, the result has 20 rows. This is called a Cartesian product. You do not write an ON clause — all combinations are generated automatically.

CROSS JOIN — WHEN TO USE IT

Build a date × product matrix good ✓
Generate all pricing combinations good ✓
Join tables with a shared ID column bad ✗ → JOIN … ON
Large tables with no WHERE filter bad ✗ — billions of rows
SQL 
SELECT
    products.name,       -- every product
    months.month_name    -- paired with every month
FROM products
CROSS JOIN months;       -- no ON clause needed
-- 10 products x 12 months = 120 result rows

Two tables of 10,000 rows each produce 100 million result rows — always add a WHERE clause or filter in a subquery before running a CROSS JOIN on large tables.

Right Join Type

Which join type fits each query question

Decision Guide

Every join type answers a different question about your data. Choosing the wrong one means silently dropping rows you needed — or generating far more rows than expected. Matching the join type to your question is the key skill.

JOIN TYPE GUIDE

Join type Use when…
INNER You only want rows that exist in both tables
LEFT You need every left row, even those with no match
RIGHT Same as LEFT, but keeping every right row instead
FULL You need all unmatched rows from both sides
CROSS Building a matrix or grid of all row combinations
SELF Comparing rows within a single table (hierarchies)
SQL 
-- INNER: only customers who have an order
FROM customers JOIN orders ON customers.id = orders.cid

-- LEFT: all customers, even those with no order
FROM customers LEFT JOIN orders ON customers.id = orders.cid

-- FULL OUTER: all rows from both, nulls where no match
FROM customers FULL OUTER JOIN orders ON customers.id = orders.cid

RIGHT JOIN is rarely seen in real codebases — most SQL developers swap the table order and write a LEFT JOIN instead, which reads more naturally left to right.

Intersection only

INNER JOIN

INNER JOIN • ON a.id = b.id

Returns rows where the join key matches on both sides. Any row without a counterpart in the other table is dropped from the result.

LEFT JOIN

LEFT JOIN • ON a.id = b.id

Keeps every row from the left table. When the right table has no match, its columns are filled with NULL.

Result · Every row from A; matched columns from B

03

Everything on the right

RIGHT JOIN

RIGHT JOIN • ON a.id = b.id

The mirror image of LEFT JOIN. Keeps every row from the right table; left-table columns become NULL when no match exists.

Result · Every row from B; matched columns from A

04

Everything on both sides

FULL OUTER JOIN

FULL OUTER JOIN • ON a.id = b.id

Returns the union of LEFT and RIGHT JOIN. Unmatched cells on either side become NULL — ideal for full reconciliation work.

Result · Every row from both tables

05

A table joined to itself

SELF JOIN

JOIN employees m • ON e.manager_id = m.id

Not a separate join type — it is any join where the same table appears twice with different aliases. Used for hierarchies, comparisons, and pair-finding.

Result · Rows of one table matched against other rows of the same table

06

Every row paired with every row

CROSS JOIN

CROSS JOIN • no ON clause

No join key. Every row from A is paired with every row from B. Useful for grids, calendars, and seed data — dangerous on large tables.

Result · The Cartesian product — every combination

Code Examples

Hands-on code snippets to explore the concepts

01

LEFT JOIN — Unmatched Rows

Beginner Customers NULL values Outer join

What This Does

This query returns every customer row and joins any matching orders — customers with no orders appear with NULL in the order column. Use it when you need every row from the left table, even those with no match on the right.

left_join_customers.sql 
SELECT
    c.name,           -- customer name (always shown)
    o.order_id        -- NULL if no matching order exists
FROM customers c      -- left table: keep every row
LEFT JOIN orders o    -- right table: match where possible
ON c.id = o.customer_id; -- join on the shared key
Terminal $ psql -f left_join_customers.sql
Alice | 1001
Bob | NULL

Add WHERE o.order_id IS NULL after the join to find only the customers who have never placed an order.

02

Self Join — Hierarchy

Beginner Employees Table aliases Manager

What This Does

This query joins the employees table to itself using two aliases — one for the staff rows and one for the manager rows. It pairs each employee with their manager's name by matching manager_id back to id in the same table.

self_join_employees.sql 
SELECT
    e.name AS employee,    -- staff alias: row for each employee
    m.name AS manager      -- manager alias: linked manager row
FROM employees e           -- first copy of the table (staff)
LEFT JOIN employees m      -- second copy of the table (managers)
ON e.manager_id = m.id;   -- link each row to its manager row
Terminal $ psql -f self_join_employees.sql
Alice | Maria
Bob | NULL

The LEFT JOIN keeps the CEO — who has no manager — in the result; a plain JOIN would silently drop that row.

03

FULL OUTER JOIN — Both Sides

Beginner Suppliers NULL detection Audit

What This Does

This query keeps every row from both tables, filling NULL wherever no match exists on either side. Use it to audit two datasets and surface entries that appear on only one side.

full_outer_join.sql 
SELECT
    c.name   AS customer,     -- NULL if no matching customer
    o.status AS order_status  -- NULL if no matching order
FROM customers c
FULL OUTER JOIN orders o      -- keep all rows from both tables
ON c.id = o.customer_id;      -- join on the shared key
Terminal $ psql -f full_outer_join.sql
Alice | shipped
NULL | pending

Filter with WHERE c.name IS NULL OR o.status IS NULL to isolate only the rows that had no match on either side.

04

RIGHT JOIN — Every Order Survives

Beginner Orders Orphaned rows Outer join

What This Does

A RIGHT JOIN is the mirror image of LEFT JOIN — it keeps every row from the right table, even when no customer matches. This surfaces orders linked to deleted customer records.

right_join_orders.sql 
SELECT
    c.name      AS customer,    -- NULL when customer was deleted
    o.order_id                  -- always shown (right table)
FROM customers c
RIGHT JOIN orders o             -- keep every order row
ON c.id = o.customer_id;        -- join on the shared key
Terminal $ psql -f right_join_orders.sql
Alice | 1001
NULL | 1002

Most analysts prefer to write LEFT JOIN and swap the table order, since it reads more naturally — but RIGHT JOIN can save a refactor when the right-hand table is the one you really want to preserve.

05

CROSS JOIN — All Combinations

Intermediate Stores & Dates Cartesian product Calendar

What This Does

A CROSS JOIN with no ON clause pairs every row from one table with every row from another. Here it builds a full grid of store × date combinations — useful for spotting days when a store reported no sales at all.

cross_join_calendar.sql 
SELECT
    s.name AS store,        -- 3 stores
    d.day  AS report_date   -- 7 days in the week
FROM stores s
CROSS JOIN days d           -- pair every store with every day
ORDER BY s.name, d.day;     -- result: 3 × 7 = 21 rows
Terminal $ psql -f cross_join_calendar.sql
Downtown | 2026-04-20
Downtown | 2026-04-21
Uptown | 2026-04-20

Always check row counts before a CROSS JOIN — a 5,000-row table joined with a 1,000-row table produces 5 million rows.

Practice Exercises

Guided exercises to reinforce your learning

01

Find Missing Data

Beginner Customers LEFT JOIN IS NULL

Your Task

You have a customers table and an orders table. Write a LEFT JOIN query that returns every customer, including those who have never placed an order. Add a WHERE clause that keeps only the customers with no orders at all. Your output should show one customer name with a NULL order ID.

find_missing_customers.sql 
SELECT
    c.name,          -- customer name from the left table
    o.order_id       -- NULL when no matching order exists
FROM customers c
LEFT JOIN orders o   -- keep every customer row
ON c.id = o.customer_id   -- join on the shared key
WHERE o.order_id IS NULL; -- filter to unmatched rows only
Terminal $ psql -f find_missing_customers.sql
Diana | NULL

This pattern — LEFT JOIN followed by WHERE right_table.column IS NULL — is the standard way to find gaps in your data, such as customers who haven't ordered, employees with no timesheet entries, or products with no sales.

02

Employee Manager

Beginner Employees Self Join Aliases

Your Task

You have a single employees table where each row has an id, a name, and a manager_id pointing to their manager's row. Write a self join query that lists each employee alongside their manager's name. Use a LEFT JOIN so that the top of the hierarchy — who has no manager — still appears in the result.

employee_manager.sql 
SELECT
    e.name AS employee,   -- staff alias: the employee's name
    m.name AS manager     -- manager alias: NULL for top of hierarchy
FROM employees e          -- first copy of the table (staff)
LEFT JOIN employees m     -- second copy of the table (managers)
ON e.manager_id = m.id;  -- link each employee to their manager
Terminal $ psql -f employee_manager.sql
Alice | NULL
Bob | Alice

Self joins work on any table where one column points back to another row in the same table — org charts, product categories, geographic regions, and comment threads all follow this same pattern.

03

Full Audit

Intermediate Products FULL OUTER JOIN NULL detection

Your Task

You have a products table and a sales table. Some products have no sales record, and some sales rows reference a product that no longer exists in the products table. Write a FULL OUTER JOIN query that returns all rows from both tables so you can see every unmatched row on either side.

full_audit.sql 
SELECT
    p.name    AS product,     -- NULL if no matching product row
    s.revenue AS sale_amount  -- NULL if no matching sales row
FROM products p
FULL OUTER JOIN sales s       -- keep all rows from both tables
ON p.id = s.product_id;       -- join on the shared product ID
Terminal $ psql -f full_audit.sql
Widget | 5000
NULL | 1200

Add WHERE p.name IS NULL OR s.revenue IS NULL to isolate only the mismatched rows — a quick way to spot data quality issues before building a report.

04

Orphaned Orders

Beginner Orders RIGHT JOIN IS NULL

Your Task

Some orders rows reference a customer_id that no longer exists in the customers table — these are called orphaned rows. Write a RIGHT JOIN query that returns every order alongside the customer name, then filter to keep only orders with a missing customer.

orphaned_orders.sql 
SELECT
    o.order_id,
    c.name AS customer        -- NULL when customer was deleted
FROM customers c
RIGHT JOIN orders o           -- keep every order row
ON c.id = o.customer_id
WHERE c.id IS NULL;           -- only orders with no customer
Terminal $ psql -f orphaned_orders.sql
1002 | NULL
1007 | NULL

Orphaned rows usually mean a foreign key constraint is missing. Many teams run this query nightly to flag broken references before they corrupt downstream reports.

Size × Color Grid

Intermediate Sizes & Colors CROSS JOIN ORDER BY

Your Task

A T-shirt vendor needs every possible size-and-color combination to seed an inventory table. The sizes table has 4 rows (S, M, L, XL) and the colors table has 5 rows. Write a CROSS JOIN that returns all 20 combinations, sorted by size then color.

size_color_grid.sql

L | Blue
L | Green

Common Mistakes

Frequent errors and how to avoid them

Using INNER JOIN When You Need LEFT JOIN

Customers with no orders are silently dropped from the result.

Pitfall

An INNER JOIN only keeps rows that match in both tables — if a customer has no orders, that row is silently removed from the result. Use LEFT JOIN whenever you need every row from the left table, even those with no matching row on the right.

Wrong — drops unmatched rows 

SELECT c.name, o.order_id
FROM customers c
JOIN orders o          -- INNER JOIN by default
ON c.id = o.customer_id;
-- customers with no orders vanish

Correct — keep every customer 

SELECT c.name, o.order_id
FROM customers c
LEFT JOIN orders o     -- keep every customer row
ON c.id = o.customer_id;
-- unmatched customers show NULL

Think of it like a guest list: LEFT JOIN prints every invited guest, marking “no show” next to those who didn't come; INNER JOIN only prints the guests who actually attended.

Forgetting Aliases in a Self Join

Without aliases, SQL cannot tell the two copies of the table apart and raises an ambiguity error.

Pitfall

A self join references the same table twice in one query. Without aliases, every column reference like employees.name is ambiguous — SQL doesn't know which copy you mean and raises an error. Always give each copy a distinct alias such as e and m.

Wrong — ambiguous column names 

SELECT name, name    -- which table's name?
FROM employees
JOIN employees       -- same table twice, no alias
ON manager_id = id; -- SQL error: ambiguous

Correct — aliases separate the copies 

SELECT e.name, m.name  -- e = staff, m = manager
FROM employees e        -- first copy: staff
JOIN employees m        -- second copy: managers
ON e.manager_id = m.id; -- unambiguous

A table alias in a self join is like giving two identical twins name badges — without the badges, nobody (including SQL) can tell them apart.

Running CROSS JOIN Without a Limiting Filter

A CROSS JOIN on large tables multiplies row counts and can crash a query or lock up the database.

Pitfall

A CROSS JOIN produces a row for every combination of rows in both tables — two tables of 10,000 rows each generate 100 million result rows. Always add a WHERE clause or pre-filter with a subquery to limit the data before the join runs.

Wrong — unfiltered explosion 

SELECT products.name, dates.day
FROM products          -- 10,000 rows
CROSS JOIN dates;      -- 365 rows
-- result: 3,650,000 rows

Correct — filter before joining 

SELECT products.name, dates.day
FROM products
CROSS JOIN dates        -- same join
WHERE products.active = true; -- limit left table first

Before running a CROSS JOIN, check how many rows each table has — multiply those two numbers to see how large your result set will be, and always add a filter if the answer is in the millions.

Filtering the Right Table in WHERE Kills the LEFT JOIN

A WHERE condition on the right table's columns silently turns a LEFT JOIN back into an INNER JOIN.

Pitfall

When you put a condition on the right table's columns in the WHERE clause, it filters out the NULL rows that the LEFT JOIN just preserved — effectively turning your LEFT JOIN back into an INNER JOIN. Move the condition into the ON clause to filter during the join instead of after it.

Wrong — WHERE drops NULL rows 

SELECT c.name, o.order_id
FROM customers c
LEFT JOIN orders o
ON c.id = o.customer_id
WHERE o.status = 'shipped';
-- silently filters out NULL rows
-- behaves like an INNER JOIN

Correct — filter inside ON clause 

SELECT c.name, o.order_id
FROM customers c
LEFT JOIN orders o
ON c.id = o.customer_id
AND o.status = 'shipped';
-- filter happens during the join
-- unmatched customers still appear

Rule of thumb: conditions on the left table belong in WHERE; conditions on the right table belong in ON when you want to keep unmatched rows.

Joining a Self Join on the Wrong Column

Joining e.id = m.id pairs every employee with themselves instead of with their manager.

Pitfall

In a self join, you must connect the foreign key on one alias to the primary key on the other. Joining e.id = m.id just pairs every row with itself, which looks fine at a glance but is meaningless. The correct join is e.manager_id = m.id.

Wrong — pairs each row with itself 

SELECT e.name AS employee,
       m.name AS manager
FROM employees e
JOIN employees m
ON e.id = m.id;
-- each row paired with itself
-- "manager" is always the employee

Correct — foreign key to primary key 

SELECT e.name AS employee,
       m.name AS manager
FROM employees e
LEFT JOIN employees m
ON e.manager_id = m.id;
-- each employee paired with their actual manager

Before writing a self join, draw the relationship: which column on alias e points to a row on alias m? That column is your join key.
